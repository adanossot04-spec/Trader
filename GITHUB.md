## 4. Варіант A — без git, через браузер (найшвидший)

1. Відкрийте <https://github.com/new>.
2. **Repository name:** `ta-assistant`. Виберіть **Public** або **Private**.
3. **Не** ставте галочки «Add a README file», «Add .gitignore», «Choose a license» — усе це вже є в проєкті,
   і зайві файли створять конфлікт при першому push.
4. Натисніть **Create repository**.
5. На сторінці порожнього репозиторію — посилання **uploading an existing file**.
6. Розпакуйте архів `ta-assistant-github.zip` (лежить поруч із папкою проєкту) і **перетягніть у браузер
   вміст папки `ta-assistant`** — саме вміст, а не саму папку. GitHub підтримує перетягування тек із папками.
7. У полі коментаря напишіть, наприклад, `Перша версія: план за 60 хв до відкриття US-ринку` → **Commit changes**.
8. Перевірте, що залилось усе: `app/`, `tests/`, `.github/workflows/ci.yml`, `LICENSE`. Вкладка **Actions**
   має показати запущений workflow `tests` (зелений, ~20 с).

> Якщо папка `.github` не залилась (браузер інколи її «з'їдає»), створіть файл вручну:
> **Add file → Create new file**, ім'я `.github/workflows/ci.yml`, і вставте вміст однойменного файлу з проєкту.

Мінус цього варіанта: історії комітів майже немає, і оновлювати код доведеться так само руками. Для постійної
роботи краще варіант B.

## 5. Варіант B — git CLI (рекомендовано)

### 5.1. Створіть порожній репозиторій

<https://github.com/new> → назва `ta-assistant` → **без** README/.gitignore/license → **Create repository**.
Скопіюйте URL — він виглядає як `https://github.com/ВАШ-ЛОГІН/ta-assistant.git`.

### 5.2. Одна команда замість десяти

```bash
cd ta-assistant
chmod +x publish.sh          # один раз
./publish.sh https://github.com/ВАШ-ЛОГІН/ta-assistant.git
```

Скрипт зробить: пошук секретів серед файлів, які пішли б у коміт → прогін 268 тестів → `git init` і перший
коміт у гілці `main` → `git push -u origin main`. Якщо щось не так (знайшовся `.env`, впав тест) — він
зупиниться **до** push і скаже, що виправити.

### 5.3. Те саме вручну (якщо хочете бачити кожен крок)

```bash
cd ta-assistant
git init -b main
git add -A
git status --short          # ПЕРЕВІРТЕ: у списку не має бути .env, data/assistant.db, data/cache/
git commit -m "Помічник для торгівлі US-акціями: план за 60 хв до відкриття ринку"
git remote add origin https://github.com/ВАШ-ЛОГІН/ta-assistant.git
git push -u origin main
```

### 5.4. Авторизація при push

- **HTTPS:** пароль не приймається. Потрібен токен:
  GitHub → аватар → **Settings → Developer settings → Personal access tokens → Fine-grained tokens →
  Generate new token** → Repository access: *Only select repositories* → `ta-assistant` →
  Permissions → **Contents: Read and write** → Generate. Далі при `git push`:
  логін — ваш нік, пароль — цей токен (зберігається в credential manager, питатиме один раз).
- **SSH:** `ssh-keygen -t ed25519 -C "ви@example.com"` → `cat ~/.ssh/id_ed25519.pub` → GitHub →
  **Settings → SSH and GPG keys → New SSH key** → вставити → і використовувати remote
  `git@github.com:ВАШ-ЛОГІН/ta-assistant.git`.

## 7. Гігієна секретів (прочитайте хоча б раз)

**Ніколи не комітьте:** `.env`, токени, пароли, реальні номери рахунків. Шаблон для нових користувачів —
`.env.example` (у ньому лише назви змінних і коментарі, без значень).

Перевірка перед комітом:

```bash
git status --short            # що піде в коміт
git status --ignored --short # що ігнорується (тут мають бути .env і data/)
git check-ignore -v .env      # покаже правило, яке закриває .env
```

**Якщо `.env` уже залетів у коміт:**

1. Приберіть із індексу (файл на диску лишиться):
   `git rm --cached .env && echo ".env" >> .gitignore && git commit -m "Прибрати .env з репозиторію"`.
2. В історії він **усе ще є** — почистіть історію: `pip install git-filter-repo && git filter-repo --path .env --invert-paths`,
   потім `git push --force-with-lease`.
3. **Обов'язково відкличте (rotate) всі ключі, які були в тому файлі** — LLM, Telegram, FRED. Після публікації

Для складної автоматизації в GitHub існують **Secrets** (Settings → Secrets and variables → Actions):
вони доступні лише під час виконання workflow і ніколи не потрапляють у git.

## 9. Результати: розклад, артефакти, GitHub Pages

Це той самий підхід, що й у ботів на кшталт
`kp-grant-radar`: **запуск за розкладом → звіт у підсумку запуску → артефакт → опублікована сторінка
результатів**. Різниця лише в тому, що тут результат — план на найближчу сесію, а не список грантів.

### Що саме робить `monitor.yml`

```
GitHub Actions (розклад у UTC, пн–пт): 12:10 · 12:40 · 13:10 · 13:40
        │
        ├─ tools/gha_gate.py — ворота: дивиться час біржі America/New_York
        │    ├─ свято NYSE або вихідний           → «Пропущено» (з назвою свята)
        │    ├─ поза вікном 07:50–09:05 ET        → «Пропущено» (це зайве вікно сезону)
        │    ├─ план уже побудовано < 45 хв тому  → «Пропущено» (щоб не дублювати Telegram)
        │    └─ у вікні                            → будуємо план на найближчу сесію
        │
        ├─ python3 run.py --propose --force       →  план + премаркет-ґеп + журнал + Telegram
        ├─ python3 tools/make_site.py --out site  →  сторінка результатів (HTML/JSON/MD)
        ├─ Artifacts: proposals-<сесія>           →  results.md, results.json, outbox.log
        └─ GitHub Pages: site/                    →  https://ВАШ-ЛОГІН.github.io/ta-assistant/
```

**Чому чотири вікна, а не одне.** GitHub виконує `schedule` у UTC і з затримкою (зазвичай 3–20 хв).
Влітку 12:10 UTC = 08:10 за Нью-Йорком, узимку те саме дає 13:10 UTC. У кожному сезоні у вікно
`07:50–09:05 ET` потрапляє два вікна (08:10 і 08:40) — друге потрібне як страхувальне, якщо перше
впало або GitHub затримав запуск на півгодини. Антидубль у воротах не дає надіслати два плани за день.

### Увімкнути GitHub Pages (один клік)

**Settings → Pages → Build and deployment → Source: GitHub Actions.**

Після цього кожен успішний прогін оновлює сторінку результатів. Адреса:
`https://ВАШ-ЛОГІН.github.io/ta-assistant/` (для репозиторію з іншою назвою — відповідно).

Якщо кнопки Source немає — репозиторій приватний на безкоштовному тарифі: GitHub Pages там вимкнено,
і публікувати сторінку не вийде. Варіанти: зробити репозиторій публічним (код і так без ключів)
або залишити результати в артефактах і в Telegram.

### Де дивитися результат

| Що | Де | Скільки живе |
|---|---|---|
| Підсумок запуску (сесія, хвилин до відкриття, причина пропуску + таблиця планів) | вкладка **Actions** → запуск → *Summary* | поки існує запуск |
| Сторінка результатів із графіками | **GitHub Pages** | до наступного оновлення (там завжди останні 10 сесій) |
| `results.md`, `results.json`, `outbox.log` | запуск → **Artifacts** | 90 днів (типово) |
| Журнал усіх планів | кеш Actions (`data/assistant.db`) | поки GitHub тримає кеш (~7 днів без звернень) |
| Готовий текст заявки брокеру в кишені | **Telegram** (якщо додали токен) | у чаті — постійно |
| `results/latest.md` + історія по сесіях | тека `results/` у самому репозиторії | назавжди (історія git) |

### Слід у репозиторії: тека `results/`

Кожен успішний прогін додає в репозиторій `results/latest.md`, `results/latest.json` і
`results/history/<сесія>.md`. Це не дублювання заради краси:

- артефакти GitHub живуть 90 днів, кеш Actions — близько 7 днів без звернень, а **git-історія залишається**;
- **GitHub вимикає розклад у репозиторії без активності 60 днів** — щоденний коміт бота тримає розклад живим
  (це варто знати всім, хто робить «ботів на Actions»: без комітів розклад одного дня просто зникає);
- динаміку видно очима: історія файлів у теці `results/` — це фактичний перелік планів по днях.

Вимкнути коміти: у `monitor.yml` змініть `COMMIT_RESULTS: "true"` на `"false"` — тоді результати
залишаться тільки в артефактах, на Pages і в Telegram.

**Про приватність.** У публічному репозиторії план бачать усі: тикери, рівні, розмір позиції, ризик у
доларах. Але там немає ні ключів, ні доступу до рахунку, і бот жодного ордера не ставить. Якщо не хочете
показувати розмір позицій — варіанти прості: приватний репозиторій без Pages (результати в Telegram і
артефактах), або `COMMIT_RESULTS: "false"` і без Pages.

### Скільки це коштує

У публічному репозиторії хвилини Actions **не обмежені** — платити нема за що. У приватному: 2000 хв/міс
безкоштовно, а прогін займає близько хвилини, тобто ~90 хв на місяць. Дані — з безкоштовних джерел
(Yahoo без ключа). Єдине, що варто тримати в голові: якщо бот вам справді потрібен **рівно о 8:30 ET,
кожної сесії, без «може затриматись»** — це не GitHub Actions, а маленький VPS (розділ 12).

## 10. Секрети й ручний запуск

### 10.1. Секрети (усе необов'язкове)

**Settings → Secrets and variables → Actions → New repository secret.**

| Секрет | Навіщо | Обов'язковий? |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | бот у Telegram (створюється в @BotFather) | ні; без нього результати лишаються на GitHub |
| `TELEGRAM_CHAT_ID` | ваш чат із ботом (`@userinfobot` підкаже id) | ні |
| `BOOK_JSON` | ваш реальний портфель — вміст `data/book.json` (капітал, позиції) | ні; без нього капітал береться з `config.yaml` |
| `OPENROUTER_API_KEY`, `GROQ_API_KEY`, `GOOGLE_API_KEY`, `OPENAI_API_KEY` | коментар від LLM (рівні все одно рахує код) | ні |
| `TWELVEDATA_API_KEY`, `ALPHA_VANTAGE_API_KEY` | запасні джерела котирувань, якщо Yahoo не відповість | ні |

Порожній секрет просто не використовується — саме тому бот працює й без жодного ключа.

### Лист на пошту через Resend (необов'язково)

План може приходити листом. Потрібні три секрети (Settings → Secrets and variables → Actions →
**Secrets**): `RESEND_API_KEY` (resend.com → API Keys), `MAIL_TO` (кому, можна кілька через кому),
`MAIL_FROM` (необов'язково). Посилання на сторінку результатів у листі підставляється автоматично
з `RESULTS_URL` у workflow — змінювати нічого не треба.

Пам'ятайте обмеження безкоштовного тарифу: поки домен не підтверджено, листи йдуть лише
з `onboarding@resend.dev` і лише на вашу реєстраційну адресу. Крок «Що пішло в Telegram і на пошту»
показує в підсумку запуску, чи лист пішов, а якщо ні — точну причину від Resend.

### Глибина аналізу в CI (нічого додавати не потрібно)

Фундаментал (SEC EDGAR), календар звітів (Nasdaq), режим ринку (Yahoo: VIX, 10-річна ставка) і
заголовки (Yahoo RSS) **працюють без жодного секрета** — ключів у них немає за визначенням.
SEC лише просить, щоб у запиті був контакт; у workflow уже підставлено
`SEC_EDGAR_USER_AGENT` (за замовчуванням службовий). Якщо хочете свій — додайте
**Settings → Secrets and variables → Actions → Variables → `SEC_USER_AGENT`**
(це змінна, не секрет; значення на кшталт `Ivan ivan@example.com`).

Час прогону: перший запуск доби (~28 с, з них глибина ~24 с — SEC і RSS тягнуться паралельно,
з повагою до ліміту SEC ≤ 8 запитів/с), повторний запуск того ж дня — близько секунди, бо
фундаментал/макро/RSS кешуються на добу (`data/cache/`). Ліміт безкоштовних хвилин GitHub Actions
це не напружує: ~40 с на запуск проти 2000 хв безкоштовних щомісяця.

Якщо SEC/Nasdaq недоступні (ліміт, збій) — прогін не падає: глибина просто буде неповною,
а в розборі це видно (порожні поля), вердикт при цьому лишається детермінованим.
Ключі ніколи не потрапляють у код і в логи: вони підставляються у змінні середовища лише на час запуску.

> **Правило про гроші:** окремо від публічних даних тримайте `BOOK_JSON` (розмір капіталу й позиції) —
> якщо не хочете показувати свої цифри, просто не додавайте цей секрет: тоді план рахуватиметься
> від суми в `config.yaml`.

### 10.2. Запустити вручну (не чекаючи розкладу)

**Actions → «Пропозиції — за годину до відкриття US-ринку» → Run workflow.** Галочка `force` (типова — увімкнена)
означає «перерахувати план навіть якщо сьогоднішній уже готовий», тобто знімає перевірки вікна й свіжості.
Так зручно подивитися, що бот видає, у будь-який момент — навіть у неділю ввечері.

Те саме локально, без GitHub:

```bash
python3 tools/gha_gate.py            # побачите рішення: працюємо чи ні, і чому
python3 run.py --propose --force     # сам план
python3 tools/make_site.py --out site --summary   # сторінка результатів як на GitHub Pages
```

## 12. А якщо треба, щоб бот працював без вашого комп'ютера

GitHub Actions для цього **не підходить**: розклад там задається в UTC, cron запускається неточно
(може «з'їхати» на 10–30 хв), а 8:30 ET зсувається між літнім/зимовим часом. Для «плану на щодень»
це не проблема — ворота `gha_gate.py` усе одно будують план за 70–80 хв до відкриття (розділ 9).
Але якщо потрібна хвилинна точність і повний контроль — зробіть так, як нижче.

Правильний варіант — дешевий VPS (2–5 $/міс) і systemd:

```ini
# /etc/systemd/system/trading-assistant.service
[Unit]
Description=Trading Assistant — план за 60 хв до відкриття US-ринку
After=network-online.target

[Service]
WorkingDirectory=/opt/ta-assistant
ExecStart=/usr/bin/python3 run.py --port 8000
Restart=always
Environment=TZ=Europe/Kyiv
User=trader

[Install]
WantedBy=multi-user.target
```

Планувальник усередині сервісу (APScheduler із таймзоною `America/New_York`) сам подбає про 8:30 ET —
жодних зовнішніх cron не треба. Для тих, хто все ж використовує системний cron:
`CRON_TZ=America/New_York` + `30 8 * * 1-5` (київський аналог у березні дає вже 9:30 ET — див. розділ
«Розклад» у README).

## 14. Якщо щось пішло не так

| Помилка | Що робити |
|---|---|
| `src refspec main does not match any` | ще немає коміту: `git add -A && git commit -m "..."`, або гілка називається `master` → `git branch -M main` |
| `Support for password authentication was removed` | потрібен токен або SSH (розділ 5.4) |
| `Updates were rejected because the remote contains work...` | репо створено з README: `git pull --rebase origin main` (дозволити різні історії: `--allow-unrelated-histories`) або `git push --force-with-lease`, якщо вміст репозиторію вам не потрібен |
| `Please tell me who you are` | `git config user.name "Ваше Ім'я" && git config user.email "ви@example.com"` |
| `Permission denied (publickey)` | SSH-ключ не доданий у GitHub (розділ 5.4) або використайте HTTPS + токен |
| `remote: error: File ... is 105 MB` | у коміт потрапив великий файл — приберіть і додайте в `.gitignore` |
| Файл `.env` видно на GitHub | розділ 7: прибрати з git, почистити історію, **відкликати ключі** |
| Workflow «Пропозиції…» завершується як «Пропущено» | так і має бути поза вікном 07:50–09:05 ET, у вихідні та на свята NYSE — дивіться *Причина* в Summary |
| Немає артефакта чи сторінки результатів | запуск пропущено воротами (не було плану) — натисніть **Run workflow** вручну з галочкою `force` |
| В Actions є лише `tests`, немає кнопки запуску | `monitor.yml` не в репозиторії — див. розділ 15 |
| Запуск червоний: «немає потрібних файлів» | завантажено не весь проєкт — розділ 15, крок 1 |
| Запуск червоний: «Pages недоступні (HTTP 404)» | приватний репозиторій на безкоштовному тарифі; план усе одно в Summary, артефактах і теці `results/` |
| Pages показує 404 | увімкніть Source: GitHub Actions (розділ 9) і дочекайтесь наступного запуску; адреса має вигляд `https://ЛОГІН.github.io/назва-репозиторію/` |
| У Telegram тиша | перевірте секрети `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`; без них план все одно є в артефактах і на Pages |
| Ціна на сторінці не збігається з брокером | у колонці «Ціна зараз» підписано, **що це за ціна**: `премаркет 08:41 ET`, `після закриття 17:05 ET` або `закриття 09.10`. Брокери з овернайт-торгівлею (24/5) показують власні позасесійні ціни — безкоштовні джерела їх не віддають. Самі рівні входу/стопу рахуються з **закритих** свічок, тому ліміт може стояти на 2–4% нижче ринку: це умова входу, а не помилка |
| **CI червоний, а локально все зелене** | раннер GitHub сам виставляє `GITHUB_REPOSITORY`, `GITHUB_ACTIONS`, `CI` та інші змінні — вони протікають у код, який читає оточення. Тест, що перевіряє таку поведінку, мусить чистити оточення через `monkeypatch.delenv(...)`, інакше він проходить локально й падає в CI (саме так було з `results_hint` і `GITHUB_REPOSITORY`) |
| У підсумку запуску немає посилання на сторінку | крок «Чи увімкнені GitHub Pages?» пише посилання CDN, навіть коли Pages вимкнені. Якщо посилання немає — застарілий `monitor.yml`: у новому кроці «Зберегти звіт і сторінку в репозиторії (results/)» тека `results/site/` оновлюється щодня |

## 15. Якщо Actions показує лише «tests»: немає кнопки запуску і немає результатів

**Симптом.** На вкладці **Actions** у лівому списку «Workflows» є тільки `tests`, кнопки
**Run workflow** для бота немає, сторінки результатів і артефактів теж немає.

**Причина — не помилка в коді.** GitHub показує кнопку ручного запуску **лише для того workflow,
файл якого лежить у репозиторії на гілці за замовчуванням** (main) і містить тригер `workflow_dispatch`.
Якщо у списку лише `tests`, значить `.github/workflows/monitor.yml` у репозиторій не потрапив —
а без нього немає ні кнопки, ні розкладу, ні результатів.

Чому файл міг не потрапити: **при перетягуванні папки у браузер приховані папки (`.github`) часто
не завантажуються** — саме тому `ci.yml` («tests») зазвичай створюють вручну, і на ньому все спиняється.
GitHub не «запускає» порожнє місце: немає файлу — немає workflow.

### Виправлення за 2 хвилини (без git)

1. **Завантажте решту проєкту.** Розпакуйте `ta-assistant-github.zip`. Перетягніть у репозиторій
   (Add file → **Upload files**) **усе, крім** папки `.github`: `app/`, `tools/`, `tests/`, `dev/`,
   `docs/`, `data/book.example.json`, `run.py`, `config.yaml`, `requirements.txt`, `README.md`,
   `.env.example`, `LICENSE`, `publish.sh`, `pytest.ini`, `GITHUB.md`. Приховані папки перетягувати
   не потрібно — робочі файли workflow створимо далі в редакторі.
2. **Створіть файл workflow:**
   **Add file → Create new file** → у полі імені введіть рівно
   `.github/workflows/monitor.yml` (GitHub сам створить папки `.github/workflows`) →
   уставте вміст однойменного файлу з архіву (можна відкрити Блокнотом) →
   **Commit changes** → *Commit directly to the main branch*.
3. **Зачекайте ~30 секунд** і оновіть вкладку **Actions**. У списку зліва з'явиться
   «Пропозиції — за годину до відкриття US-ринку».
4. **Запустіть вручну:** відкрийте цей workflow (клік по назві зліва) → праворуч кнопка
   **Run workflow** → гілка `main` → **Run workflow**. Ця кнопка є **тільки на сторінці самого
   workflow**, її не видно на загальній сторінці «All workflows».

Через 1–2 хвилини в запуску буде: підсумок із таблицею планів, артефакт `proposals-<сесія>` і коміт у
теці `results/`. Якщо увімкнете Pages — ще й сторінка результатів.

> **Альтернатива без копіювання 170 рядків.** Завантажте файл `monitor.yml` у корінь репозиторію
> (звичайний drag&drop одного файлу працює), відкрийте його → олівець **Edit** → у полі з іменем
> файлу замініть `monitor.yml` на `.github/workflows/monitor.yml` → **Commit changes**. GitHub
> перенесе файл у потрібну папку.

### Оновити файли в репозиторії без git (2 хвилини)

Коли код змінюється (наприклад, розширено список тікерів або виправлено крок Pages), у браузері
це робиться так — **без** перезаливання всього проєкту:

1. Відкрийте файл у репозиторії (наприклад `config.yaml` або `.github/workflows/monitor.yml`)
   і натисніть **олівець** (*Edit this file*).
2. **Ctrl+A** → **Ctrl+V** (вставити новий вміст із архіву) → **Commit changes** →
   *Commit directly to the main branch*.
3. Якщо файлу в репозиторії ще немає — **Add file → Create new file**, введіть ім'я зі слешами
   (`.github/workflows/monitor.yml`) і вставте вміст.

Для списку тікерів цього можна й не робити: список лежить у `config.yaml`, а якщо база вже створена,
нові тікери додадуться автоматично (seed додає відсутні, вже наявні не чіпає).

### Увімкнути сторінку результатів (найчастіша пауза)

Симптом: запуск зелений, job «План на найближчу сесію» ✅, а **«Публікація результатів на GitHub
Pages» — пропущено**, сторінки немає. Причина одна: **Pages у репозиторії не увімкнені** (GitHub
не створює сайт сам собою). Для публічного репозиторію це один клік:

1. **Settings → Pages** → розділ *Build and deployment* → **Source: GitHub Actions**.
2. **Actions → «Пропозиції — за годину до відкриття US-ринку» → Run workflow** (галочка `force`).
3. Через 1–2 хвилини сторінка з'явиться за адресою
   **`https://ЛОГІН.github.io/НАЗВА-РЕПОЗИТОРІЮ/`** — саме з назвою репозиторію, а не з назвою теки
   проєкту. Наприклад, репозиторій `Trader` → `https://ЛОГІН.github.io/Trader/`.
   Точну адресу кожен запуск пише в підсумок (*Summary*): рядок «🔗 …».

**Чому це ручний крок, а не автоматичний.** Створення сайту Pages — операція рівня адміністратора
репозиторію: `POST /repos/{owner}/{repo}/pages` (це саме те, що робить `configure-pages` з
`enablement: true`). Токен workflow (`GITHUB_TOKEN`) таких прав не має **за жодних** записів у
`permissions:` — GitHub навмисно не дає автоматичному токену адмініструвати репозиторій. Спроба
завжди закінчується `Resource not accessible by integration` (це підтверджують і самі розробники
`configure-pages`: параметр `enablement` вимагає PAT або токена GitHub App). Тому в нашому workflow
кроків самоувімкнення немає — замість них:

* **сторінка результатів працює одразу** — workflow комітить її в теку `results/site/`, а в підсумку
  запуску пише робоче посилання через CDN (`cdn.jsdelivr.net/gh/…/results/site/index.html`);
* коли ви ввімкнете Pages своїм кліком, посилання стане офіційним `github.io`, і все працюватиме
  без жодних змін у файлах.

**У приватному репозиторії** на безкоштовному тарифі Pages недоступні взагалі — там сторінка не
з'явиться, доки репозиторій не стане публічним. Результати тоді беруть з *Summary*, артефактів і
`results/latest.md`.

### Що не заливається перетягуванням: приховані файли

Браузер не відправляє файли й теки, названі з крапки. Тому після drag&drop у репозиторії бракує:

| Файл | Навіщо | Як додати |
|---|---|---|
| `.github/workflows/monitor.yml` | розклад і публікація результатів | *Add file → Create new file* з ім'ям `.github/workflows/monitor.yml` |
| `.github/workflows/ci.yml` | тести на кожен push | так само |
| `.gitignore` | щоб `data/` і `.env` не потрапили в репозиторій | *Create new file* з ім'ям `.gitignore` |
| `.env.example` | шаблон ключів для інших | *Create new file* з ім'ям `.env.example` |

Правило просте: **якщо у файлу чи теки назва починається з крапки — його треба створити вручну**
в редакторі GitHub (ім'я вводиться разом зі слешами, GitHub сам зробить потрібні теки).

### Якщо запуск став червоний

- **«У репозиторії немає потрібних файлів: …»** — завантажено не весь проєкт (див. крок 1). У підсумку
  запуску буде перелік того, чого не хватає.
- **«git: command not found»** або помилка кроку «Зберегти звіт» — у `monitor.yml` поставте
  `COMMIT_RESULTS: "false"` (тоді план не комітитиметься, але все інше працюватиме).
- **Job «Публікація результатів на GitHub Pages» пропущено** — так і має бути, поки Pages не
  увімкнені. Сторінка при цьому все одно є: у підсумку запуску рядок
  «🌐 Сторінка результатів (працює без налаштувань)» із посиланням через CDN. Хочете офіційну адресу —
  **Settings → Pages → Build and deployment → Source: GitHub Actions**, і наступний запуск опублікує
  сайт уже на `github.io`. Нічого в коді змінювати не треба.
- **Запуск зелений, але «Пропущено»** — так працюють ворота: поза вікном 07:50–09:05 за Нью-Йорком,
  у вихідні та на свята NYSE. Натисніть **Run workflow** ще раз із галочкою `force`.

### Чому краще не мішати два проєкти в одному репозиторії

Якщо ви вантажите помічника в репозиторій іншого бота (наприклад `kp-grant-radar`), то в ньому
змішуються два `.gitignore`, два `requirements.txt` і різні workflow — і будь-яка зміна одного може
зламати іншого. Створіть окремий репозиторій: <https://github.com/new> → назва `ta-assistant` →
**без** README/.gitignore/license → і виконуйте кроки вище.
